## 5.1 Overview of the implemented system

The implemented application is a web data catalog for outputs of machine learning models trained on longitudinal administrative patient data. It works as a single-page application, accessible through a standard web browser. The user opens one URL and then navigates between several views without full-page reloads. The backend is a containerized REST API with a separate worker process for asynchronous predictions, as described in Section 4.2. For this chapter the focus is on what the user actually sees and can do, not on the architecture.

The application has five main areas, each reachable from the top navigation bar (Fig. 5.1): Home, Scoring Form, Prediction History, Training Data, and Models. Also there is a Datasets page and a personal Account page. The Training Data area is the entry point for the RWE analyst persona, and it contains the longitudinal data visualizations. The Scoring Form area is the entry point for the clinical specialist persona, who wants to get a prediction for a new patient. These two flows share the same medical code dictionary, the same model registry, and the same authentication layer.

In the development database, the catalog currently holds 22,282 patient records. One patient has on average tens to hundreds of five-digit procedure codes, with big variation between patients. For example, patient 49 has 332 codes, 64 distinct codes, and seven predictions made by different models, with an estimated accuracy of 86 % (Fig. 5.4). These numbers are used across the thesis as a reference case.

All features described in the following sections are implemented and working. Some parts are only in a first functional version. For example, the wireframe-based usability testing from Section 4.3.4 was done on paper mockups, not on the deployed application, and the bulk JSON upload is more limited than the CSV one. These limitations are listed again in the Discussion in Chapter 6.

## 5.2 Training data catalog and longitudinal data visualization

Longitudinal patient data is hard to read in raw form. One patient can have hundreds of five-digit procedure codes, and the ordering, frequency, and clinical specialty of each code all matter. So the catalog offers three coordinated views of the same data. The first one is a list view where each patient is a row with a short code preview and a model accuracy summary. The second one is an accuracy heatmap over the whole catalog, where each patient is a column and each scoring category is a row. The third one is a per-patient detail view with a smaller heatmap and the full code sequence with several color-coding options. This pattern of overview plus detail is a standard approach for interactive visualization of electronic health records \autocite{borland2014innovative, wang2021ehrstar, sedig2020datadriven}.

### 5.2.1 Catalog list view

The list view (Fig. 5.2) is the default tab of the Training Data page. It shows one row per patient. Each row contains the patient ID, a preview of the first five procedure codes as rounded badges, a counter with the total code count ("+41", "+480"), the number of predictions made for this patient, and the estimated accuracy averaged across all predictions for this patient. Estimated accuracy is here defined as the proportion of model predictions that agree with the ground-truth label stored together with the record. A "Detail" button on each row opens the patient detail view described in Section 5.2.3.

The list is paginated. The default page size is 20 rows, and the user can change it. For the current database of 22,282 records this gives 1,115 pages, which is shown next to the page selector. A total-record counter is also kept in a pill element in the header of the page ("Total records: 22,282"), so the user knows immediately how big the dataset is. Pagination was chosen over infinite scroll because clinicians wanted to be able to jump to a specific page and come back to it later. Infinite scroll loses the position when the browser tab is closed.

Above the list there are two search inputs. The first one searches by Patient ID. The second one searches by a specific procedure code, and it highlights every cell where this code appears in the preview badges. So the user can scan which patients in the current cohort have a given code. We chose to implement this highlighting by synchronizing the search term with a URL query parameter, which is explained in more detail in Section 5.2.5.

### 5.2.2 Accuracy heatmap over the catalog

The second tab on the Training Data page is the Accuracy Heatmap (Fig. 5.3). It is a compact matrix view designed for the RWE analyst persona. Each column represents one patient, identified by the patient number (1, 2, 3, ...). Each row represents one scoring category: ICD10 Multiclass, ICD10 Binary, and Active Phase. The cell value is the per-patient accuracy of all predictions made in that scoring category, from 0 % to 100 %.

The cell color encodes the same number once again. We used a single-hue sequential purple colormap. 0 % accuracy gets a very light color close to white, and 100 % accuracy gets a deep purple. The specific formula is a direct function in HSL space: the hue is fixed at 270 (purple), the saturation is fixed at 80 %, and the lightness goes from 85 % at 0 % accuracy to 14.5 % at 100 % accuracy. So low and high values are easy to distinguish at a glance, even in a dense view where many columns are next to each other. Single-hue sequential palettes are recommended for ordered data where the reader needs a clear sense of "more" or "less" rather than a categorical difference \autocite{tseng2024categorical}. We chose it over a diverging (red-green) palette because there is no natural zero point in the middle of the scale. Also, the text of the percentage is overlaid on the cell and automatically switches from black to white when the cell lightness drops below 50 %, so the number is always readable. The colormap is implemented without a charting library, only with the built-in d3-scale-chromatic package and plain CSS \autocite{hFigures2016}. Compared to full charting libraries like Chart.js or Recharts, this keeps the JavaScript bundle small and the rendering fast even with many visible cells.

The heatmap uses the same pagination controls as the list view and shares the same URL state. So when a user filters the list to a specific patient ID or a specific code and then switches to the heatmap tab, the heatmap is narrowed down the same way. This way the two views stay synchronized.

### 5.2.3 Patient detail view

When the user clicks "Detail" on a row in the list view, they are taken to the patient detail page (Fig. 5.4). At the top there is a row of four summary counters: total codes, distinct codes, number of predictions, and estimated accuracy. For patient 49 these values are 332, 64, 7, and 86 %. These four numbers answer, on one glance, how long this patient history is, how diverse the code vocabulary is, how many models were evaluated on it, and how well the models did on average.

Below the summary there is a smaller per-patient heatmap. It has the same three category rows as the catalog-level heatmap (ICD10 Multiclass, ICD10 Binary, Active Phase) but the columns now represent individual predictions made for this one patient, ordered in time (1, 2, 3, ...). The color scale is different here. A binary green/red coding is used, where green means the model prediction agrees with the ground-truth label and red means it does not. So a row of green cells is easy to scan, and any red cell is a moment where the model failed for this patient. This kind of chronological agreement view makes it easy to spot whether the model was wrong at the beginning of the record, at the end, or consistently \autocite{perer2012matrixflow, plaisant2018pharmacovigilance}.

### 5.2.4 Color-coding modes for the code sequence

Under the heatmap there is the full sequence of procedure codes for this patient, displayed as a grid of rounded code badges (Fig. 5.4, bottom). For patient 49 this is 332 badges in chronological order. Raw badges alone are not easy to read, so four alternative color-coding modes are offered. The user switches between them with a tab row above the list (Specialty, TF-IDF (0), TF-IDF (1), Frequency). A legend below the tabs explains what the colors mean in the active mode.

The Specialty mode colors each badge by the medical specialty of the procedure (for example clinical oncology, pulmonology, fysiology). Codes that cannot be mapped to a known specialty are shown in white with an "Uncategorized" legend entry. This gives the reader a sense of which department the patient interacted with at each visit. On hover, the full Czech name of the specialty is shown as a tooltip (for example "Kontrolní vyšetření pneumologem, pneumologie a fzieologie").

The TF-IDF (0) and TF-IDF (1) modes visualize how informative each code is for a given class label, using the Term Frequency-Inverse Document Frequency weight described in Section 4.1.2 \autocite{tfidf_icd_codes_2022}. Higher TF-IDF means the code is more specific for the selected label. Codes with a TF-IDF above a threshold are shown in a darker shade, so the clinician can visually pick out which procedures in the history most strongly drive the prediction toward label 0 or label 1. This is a simple form of feature-importance highlighting on top of a classical TF-IDF representation, and it helps to open the black box of the classifier \autocite{humbert2021structuring}. It is also the reason why both label 0 and label 1 have their own tab. So the user can switch between them and see which codes push the prediction one way and which push it the other way.

The Frequency mode colors each code by how many times this specific code appears across the whole training catalog. Rare codes are shown in light color, frequent codes in dark gray. So the user sees at a glance if the patient history is dominated by routine procedures or if it contains unusual ones.

Each of these modes uses a different sequential color scale from d3-scale-chromatic. The same color scale is used consistently inside one mode, so the user does not have to re-learn the legend for every patient. For the Specialty mode, which is categorical and not sequential, a qualitative palette is used instead, because categorical data needs hue variation and not lightness variation \autocite{tseng2024categorical}.

### 5.2.5 Filtering, pagination, and URL-based highlighting

All filter values in the catalog are stored in the browser URL, not only in component memory \autocite{sematic2023deeplinks}. For example, when the user searches for the code 89131, the URL becomes /catalog?code=89131 and every badge with value 89131 in the current page is highlighted. When the user then clicks "Detail" on patient 49, the code query parameter is passed along, so on the detail page the same code stays highlighted in the full 332-code sequence. And when the user clicks "Back to Catalog", the previous filter is restored. So the user does not lose their context.

This approach has two practical advantages. The first one is reproducibility. A clinician or an RWE analyst can copy the current URL and send it to a colleague, and the colleague sees the exact same filtered view after login. This is important for collaborative analysis of patient cohorts. The second advantage is that the browser Back and Forward buttons work naturally inside the single-page application, because every filter change produces a new history entry.

The URL also stores pagination information. So a bookmark to page 42 of the heatmap view keeps the pagination offset and the current tab. These small details together make the catalog feel like a regular website and not like a state-heavy web application, which was one of the goals from the UX flow in Section 4.3.2.

Client-side caching is used on top of the URL state to avoid redundant backend calls \autocite{caching_ui_performance}. When the user moves from page 1 to page 2 and back to page 1, the first page is served from the cache. The same cache also serves the medical code dictionary used by the autocomplete in the scoring form (Section 5.3.3). So the autocomplete responds instantly, without a backend query for every keystroke. The medical code dictionary is loaded once per session, which is enough because it rarely changes.

# Part D — Summary of sources used (with relevance)

1. Borland, West & Hammond (2014), JAMIA — a systematic review of 17 years of EHR visualization. Grounds the choice of "overview + detail" pattern used in the catalog.
2. Wang & Laramee (2021/2022), Computer Graphics Forum — "EHR STAR" state-of-the-art survey of interactive EHR visualization. Useful both here and in the State of the Art chapter.
3. Sedig, Rostamzadeh & Abdullah (2020), MTI — activity-and-task analysis framework for EHR interactive visualization tools. Directly supports the UX-driven decisions described in 5.2.
4. Tseng, Wang, Quadri & Szafir (2024), EuroVis — empirical study of sequential vs diverging vs categorical color palettes. Used to justify the single-hue purple heatmap and the categorical Specialty palette.
5. Ledesma, Nieminen & Al-Musawi (2016), BMC MIDM — hFigures JavaScript library for health data visualization. Cited as an example of lightweight, library-minimal visualization, which matches the custom heatmap implementation.
6. Perer & Sun (2012), AMIA — MatrixFlow, a matrix-based time-evolving visualization for patient event sequences. Directly supports the "red/green chronological agreement" design of the per-patient heatmap.
7. Ledieu, Bouzillé, Plaisant et al. (2018), Frontiers in Pharmacology — time-related GUI and timeline visualizations for EHR, tested with clinicians. Supports the clinical usability argument for a detail timeline.
8. Humbert-Droz, Mukherjee & Gevaert (2022), JMIR Medical Informatics — TF-IDF with logistic regression on clinical text, including interpretation via important words. Backs the TF-IDF color-coding mode as an interpretability tool.
9. Zhan et al. (2021), Patterns — TF-IDF and other NLP techniques on clinical notes, showing good AUROC with interpretable features. Reinforces the TF-IDF interpretability argument.
10. Sematic (2023), blog — engineering write-up on deep linking in React SPAs via URL hash/query parameters. Used to cite the URL-state pattern of the catalog.
11. Nielsen (1993), NN/g — the classic 0.1 s / 1 s / 10 s response-time limits. Cited for the client-side caching argument.
